# Managed WhatsApp identity: source contract

Feature-only overlay for NEXI Channels. No deployment or real WhatsApp operation is enabled by this source task. Upstream remains pinned to `e273b904d53f5726970fd6a244ed9caa61dfeb9a`; Baileys remains the lockfile's `7.0.0-rc13`.

`patch-trusted-baileys.mjs` checks exact decoder-path and event-buffer digests. It inserts observation after successful peer decrypt and before `cleanMessage` in the authenticated `CB:message` handler. `nexi-identity.cjs` stores only raw ID, PN/optional LID, origin and a public-session digest in an object-identity WeakMap. The original message object crosses the pinned Baileys event buffer; copies or artificial `notify` events have no capability. Group/broadcast/status/own/history/stub/placeholder/protocol/decrypt-failure inputs and LID without stanza-proven PN are excluded.

Raw PN/LID device suffixes are parsed deterministically only after the exact stanza/key comparison. Removing the device suffix preserves the same logical identifier; cache aliases and regional telephone guesses cannot participate in this derivation.

Evolution consumes the capability before `prepareMessage`, authenticates `identity.observed` to NEXI, and binds the prepared object to the backend reservation. `createConversation` for managed inbound requires this reservation and compares configured account/Inbox. It uses the reserved display ID and cannot choose an editable phone/contact/cache match. Cached managed branches are closed, including another-Inbox conversations. Unmanaged behavior is unchanged. After Chatwoot creates a message, `identity.correlated` sends the actual message database ID plus the backend-owned reservation. Rails loads and checks the actual message and all ownership; it never interprets message IDs as conversation display IDs. Confirmed duplicates skip Chatwoot history creation.

Identity events contain metadata only, never message/media/PIX/QR/private session keys. They use the existing per-instance HMAC. Retries retain logical UUID/body and refresh timestamp/signature on every attempt. `signedEventClient` also refreshes managed connection/QR retries and rejects body divergence. Existing managed webhook policy is bounded to six attempts with a five-second minimum initial delay and capped exponential jitter; identity metadata has three ten-second attempts with exponential jitter. No retry is introduced for Chatwoot creation or financial outbound. Old receiver timestamps remain rejected even when a receipt exists. This correction makes no claim about the cause of historical HTTP 500 responses.

Managed financial `sendButtons` accepts only the backend recipient contract. Copy/url and native-pix shapes without a valid proof fail closed; signed operations are restricted to one controlled copy/url button. The HMAC domain is `financial-recipient:v1`, using the existing instance event secret. Base64url JSON claims bind `[version, instanceName, instanceId, pnJid, associationId, generation, deliveryId, accountId, inboxId, expiryMs, dtoSha256, sessionIdentity]`. The complete DTO hash includes number/title/description/footer/button type/display text/copy value/URL. The session digest must match the actual socket credentials, including at the final Baileys wire boundary. No arbitrary mentions, quote, regional phone variants or additional fields are authorized.

`nexi-financial-transport.cjs` uses AsyncLocalStorage for that exact recipient through the real resolver and sender. It requires durable Redis and consumes the signed operation atomically before sending. Its Redis keys are separate from Chatwoot webhook keys and cannot be lease-reclaimed. It compares the resolved JID to the proved PN and checks the actual JID immediately before `client.relayMessage`, including instance identity, expiry and one-relay state. PN A/cache alias B or any LID is a failure with zero relay. The patched Baileys relay repeats the check on the final stanza before `sendNode`, vetoes another peer/device or unproved peer LID, and independently allows only authenticated own companions. No heuristic PN/LID equivalence is accepted. Financial resolver calls do not expand/save `IsOnWhatsapp` aliases; global indexes and unmanaged cache behavior stay intact.

Financial messages are excluded from Baileys' native recent-message retry cache on both initial relay and authenticated `fromMe` echo. Evolution supplies a runtime-owned managed socket scope before creating Baileys. Admitted financial relay generates a reserved hexadecimal message ID (`3EB0F1A9C7D5E3B1` plus eight random bytes), overriding any caller-selected ID. This denial marker carries no recipient, claim, PIX or secret and survives echoes and payload reconstruction. Native-flow copy/url structure within that managed scope also denies legacy unmarked entries; editable display text is never the classifier or authority.

The patched `sendMessagesAgain` consumer independently rejects financial messages after both recent-cache lookup and `getMessage` fallback, even with absent/expired/replaced financial ALS. Cache insertion prevention alone is insufficient: pinned Baileys checks the cache before invoking Evolution's callback. The managed callback also denies marked IDs, CTA content, redacted financial placeholder and empty/missing DB fallback. A pre-relay ID/classification guard and the final stanza guard reject managed financial traffic without current transport context. Unmanaged sockets, including generic copy/url CTAs and their echoes/retries, retain baseline behavior; ordinary managed messages retain retries too. No retry scheduler, financial replay payload cache or outbound recovery is added.

`identity-foundation-source.test.cjs` executes the actual pinned decoder, real MessageRetryManager, transformed retry receipt/consumer and wire slices with synthetic IO. A pristine-source control reproduces echo/cache/native retransmission with no `getMessage` call. The corrected control emits one admitted outbound and zero second relay/sendNode with recent cache enabled and DB OFF, then forces a stale cache entry and again gets zero relay. Additional cases cover both lookup branches, nested copy/url CTA forms, reconstructed marked IDs, absent ALS, expired/replaced context, final-wire denial and generic unmanaged retries. These are source proofs; real WhatsApp wire/message-ID compatibility remains an operational gate.

Failure, success, webhook, persistence and asynchronous CTA echo redaction remain in the existing financial path. PIX and recipient tokens are not logged or returned as Chatwoot history. The backend continues to own idempotent financial history/recovery; outcome uncertainty cannot reopen the operation.

Docker applies the source transformations before build, retains pristine source for executable regression tests and copies patched Baileys plus the same CJS helper into the runtime. The pinned tsup config is also patched to keep Baileys and all three helpers external, preventing duplicated WeakMap/AsyncLocalStorage owners. A lightweight esbuild fixture executes that actual transformed config and verifies shared runtime imports; the complete image/provider bundles were not built locally. EasyPanel must verify both provider bundles, runtime module sharing, pinned dependency compatibility, actual Redis Lua/durability, Rails PostgreSQL migration/guards, two-phase ACK and readiness. The source tests run transformed code with synthetic IO; they are not proof of real authentication, pairing or WhatsApp delivery.

The complete shared-owner, ledger/revocation/issuer/admission contract is documented in the APP feature's `docs/channels/WHATSAPP_IDENTITY_FOUNDATION.md`. Historical contact adoption, automatic reattestation of tombstones, destructive merge/purge and cancel-after-admission semantics remain deliberately closed; they require separately reviewed protocols. Nothing in this overlay creates an alternative financial delivery endpoint in NEXI.
