# S12 receive owner generation — prepared candidate

Base: `f248f1ede50ec2d5519cef0ba4c391a49d6124b4`. No runtime changes, migration, build, test, service start, message or replay was executed. This adds a receive protocol; it grants no physical-send capability. The APP counterpart and exact final heads require independent static review together.

## Cause and new intake boundary

The baseline lane is `digest([scope, session, PN])`; its first non-succeeded identity_pending journal blocks later delivery. A new callback timestamp cannot renew its signed accepted_at. Existing old journals remain permanent and are never copied into the new Source table, re-signed, marked successful, moved, replayed or re-enqueued.

With `NEXI_WHATSAPP_OWNER_GENERATION_ENABLED=true`, the first *new* raw message observed behind a `recoverable_failure/identity_pending` head immediately establishes a source floor. There is no ten-minute wait on that head. Before accepting the new raw source, scope sequence S is saved as the immutable root `sourceFloorSequence`; the source is accepted once at S+1 with the original v1 HMAC, UUID, dedup key, payload digest, original accepted_at and raw payload. It is stored in `NexiIngressOwnerSource`, never in the old lane. The triggering witness therefore remains deliverable after activation. The failed journal that established identity_pending before this boundary remains explicit recoverable historical evidence; this protocol does not manufacture a delivery result for it.

Every later raw source for that root is retained through the same durable boundary, including while approval/registration is pending and after activation. Scope admission pending counts include sources before there is a delivery journal, under the existing limit 10,000 and 1 MiB payload limit. Failure/backpressure occurs before the pinned decoder's receipt. Original proof/payload and source sequence are immutable; no memory queue substitutes for acceptance. Pending states produce allowlisted owner/source diagnostics. No message content, PN/LID, secrets or arbitrary exception text is logged.

## Cutover and authorization contract

`ingress.owner_candidate` sends `{version:1, observation:<original receiver data plus v1 ingress proof>, cutover}` over the existing authenticated event channel. The exact cutover is `{version,id,old_lane,scope_id,C,R,source_floor,witness_journal_id,witness_proof_digest,snapshot_digest,generation_id,new_lane}`. C is the prior scope sequence at the first pending proposal; its snapshot includes only existing old-lane journals at or below C. R is the root revision, changed on ownership transitions rather than each staged source. `source_floor` is the immutable sequence immediately before this root's first Source acceptance; repeated generations preserve it. The new lane is `digest(['ingress-owner-generation:v1', root_lane, generation_id])`, with stable root_lane=`digest([scope,session,PN])`.

The APP authenticates normal administrator membership/authority and proves exact historical PN/LID, same sender lineage, current session and scope before approving. Evolution cannot approve. APP exports Ed25519 canonical-byte claims with purpose `whatsapp_ingress_owner_generation`, binding exact account/inbox/instance/session/PN/LID, authorization and generation IDs, C/R/source_floor, lanes, witness and snapshot digests, original proof, approved_at and expires_at. Evolution verifies them with pinned `NEXI_INGRESS_OWNER_PUBLIC_KEY` and `NEXI_INGRESS_OWNER_PUBLIC_KEY_ID`; the independent APP private/receipt keys are never installed in Evolution. Proof/approval eligibility remains at most 600 seconds from the original fresh witness, with no renewal of timestamps.

An unexpired proposal stays immutable while more sources arrive. A later *new* immutable source can create a distinct fresh proposal after expiry; old sources and proposals are unchanged. The same old-lane snapshot/C and source floor remain fixed while awaiting this transition. There is no approval-by-boolean or callback-driven administrative consent. Sources accepted since this explicit new protocol floor are durable intake governed by its receive-generation policy; they are distinct from legacy journals in the frozen prefix. An old legacy journal cannot become a Source: cross-table dedup, source fresh-at-insert checks and permanent journal identity prevent that conversion under the required restricted DB role.

Installation holds the scope lock, validates root revision and snapshot again, and requires no active/uncertain prefix work or lease token. A non-null expired lease token remains busy because an old HTTP operation may still be in flight; a timestamp alone is expired only when its token is null. An abandoned token requires separate owner reconciliation, never automatic cutover. Snapshot rows may be succeeded or safely persisted/identity_pending, with no association/ACK/continuation/materialization for unfinished rows. No outcome_unknown or uncertain creation is bypassed. Installation writes only new ownership metadata and an empty new lane; the old prefix and its pending counters are untouched. Persistent freeze guards and scheduler exclusion prevent old-lane work and pruning.

`ingress.owner_installed` returns the exact cutover/witness/authorization. The APP activates its successor atomically and returns signed `whatsapp_ingress_owner_generation_registered` claims binding authorization, generation, scope, lane and registration time. Evolution verifies that registration was minted within approval expiry, and persists it exactly once. No Source is materialized until this readback exists. A lost response is retrieved idempotently. If APP never activated before expiry, a later fresh source can propose a subsequent generation, freezing the unused intermediate lane without changing the old evidence; no expired authorization is reused. APP must reject arbitrary supersession of an already active, materialized owner and enforce its current identity chain.

## Exactly one delivery per new source

After registration, the normal pump flushes immutable Sources in increasing original sequence for each root, using a bounded batch and fair root rotation. Future raw messages need no new owner approval while that generation remains current and proved. Within the scope transaction it creates exactly one permanent `NexiIngressOwnerDelivery` link and one delivery journal, retaining the Source UUID J as the journal UUID. The global dedup key remains provider/account/inbox/instance/session/external-message-ID across Sources and Journals. SQL guards and unique keys prevent either path admitting the same source twice, including mixed-image attempts.

Version 2 claims preserve the v1 original fields and add `owner_generation_id`, `cutover_digest`, `source_journal_id=J`, `source_proof_digest`, the entire original v1 `source_proof`, original `source_sequence`, and a distinct newly reserved `delivery_sequence`. V2 uses domain `ingress:v2:<instance>`; original proof remains `ingress:v1:<instance>`. Both MACs and equality of UUID, scope, observation, original accepted_at and payload digest are verified. Source sequence must be above the approved source floor; delivery sequence must be above C and source sequence. The journal's ordering sequence is the delivery sequence. No original acceptance timestamp is replaced.

The APP must independently verify this entire provenance and active generation, reject v1 attempts to use its owner-generation successor, and reserve admission by the same original source J. Normal message creation/reconciliation/correlation then retains its existing dedup, uncertain-create checks, owner fencing and exactly-once source result. Closed conversations remain closed; the APP lifecycle creates new conversations after closure. HTTP 200 alone proves no message materialization or physical send.
